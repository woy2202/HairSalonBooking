OPIS WATKOW, ASYNCHRONICZNOSCI I PRZETWARZANIA W TLE W APLIKACJI SALONU FRYZJERSKIEGO
=====================================================================================

Projekt: HairSalon Booking
Backend: ASP.NET Core / C#
Baza danych: Azure Cosmos DB
Komponenty Azure uzyte w przeplywach asynchronicznych:
- Azure App Service
- Azure Cosmos DB
- Azure Queue Storage
- Azure Functions
- Azure Communication Services Email
- Azure SignalR Service
- Azure Application Insights / logi


1. NAJWAZNIEJSZA INFORMACJA: CZY W APLIKACJI SA RECZNIE TWORZONE WATKI?
------------------------------------------------------------------------

W aplikacji NIE tworzymy recznie watkow przez:

    new Thread(...)
    Task.Run(...)
    BackgroundWorker

To jest celowe. W nowoczesnych aplikacjach ASP.NET Core zwykle nie tworzy sie recznie watkow, bo serwer sam zarzadza pula watkow. Zamiast tego uzywamy:

    async
    await
    Task<T>
    CancellationToken
    Azure Queue Storage
    Azure Functions
    SignalR

Czyli w praktyce mamy kilka "watkow pracy" albo "przeplywow asynchronicznych", ale nie sa to recznie zarzadzane watki systemowe.

Najprosciej:

    - ASP.NET Core obsluguje request HTTP z puli watkow.
    - Gdy kod czeka na Cosmos DB, Blob Storage, Queue Storage albo Email API, uzywa await.
    - await zwalnia watek serwera na czas oczekiwania.
    - Po zakonczeniu operacji I/O wykonanie jest kontynuowane.
    - Dluzsze zadania, np. wyslanie maila, sa oddelegowane do Azure Queue + Azure Function.

To jest poprawny, skalowalny styl pisania backendu w C#.


2. DLACZEGO UZYLISMY ASYNCHRONICZNOSCI?
---------------------------------------

W aplikacji salonu fryzjerskiego wiele operacji zalezy od zewnetrznych uslug:

    - zapis wizyty do Cosmos DB,
    - odczyt klienta, fryzjera i uslugi z Cosmos DB,
    - wrzucenie wiadomosci do Azure Queue Storage,
    - wyslanie maila przez Azure Communication Services,
    - wyslanie powiadomienia SignalR,
    - zapis plikow do Azure Blob Storage.

Kazda z tych operacji moze trwac dluzej niz zwykle obliczenie w pamieci, bo wymaga komunikacji przez siec. Gdybysmy robili to synchronicznie, watek serwera bylby zablokowany i nie moglby obslugiwac innych uzytkownikow.

Dlatego metody sa zapisane jako:

    public async Task<...>

i korzystaja z:

    await ...

Dzieki temu API moze obslugiwac wielu klientow jednoczesnie bez recznego tworzenia watkow.


3. GLOWNY WATEK BIZNESOWY: KLIENT TWORZY WIZYTE
------------------------------------------------

Najwazniejszy scenariusz aplikacji:

    1. Klient tworzy wizyte w Swaggerze albo w przyszlej aplikacji frontendowej.
    2. Request trafia do AppointmentsController.
    3. Controller przekazuje dane do AppointmentBookingFacade.
    4. Facade sprawdza klienta, fryzjera, usluge i dostepnosc terminu.
    5. Wizyta jest zapisywana w Cosmos DB.
    6. Aplikacja publikuje zdarzenie "appointment booked".
    7. Kilka handlerow reaguje na zdarzenie:
       - zapis informacji do Blob Storage,
       - wrzucenie wiadomosci do Azure Queue,
       - wyslanie powiadomienia SignalR.
    8. Azure Function odbiera wiadomosc z kolejki.
    9. Azure Function wysyla maila z potwierdzeniem wizyty.

To jest rozdzielone na kilka mniejszych przeplywow, zeby endpoint tworzenia wizyty nie musial bezposrednio robic wszystkiego sam.

Najwazniejsza jest linia 32:

Co robi CancellationToken?

CancellationToken pozwala przerwac prace, jesli klient przerwie request, polaczenie zostanie zamkniete albo serwer bedzie musial anulowac operacje. Ten token jest przekazywany dalej do repozytoriow, kolejki i innych operacji.

Kod jest elastyczny. Rezerwacja wizyty i dodatkowe reakcje sa rozdzielone.

----------------------------------------------------

    linie 35-37:

    linie 39-51:
    zbudowanie payloadu JSON

    linia 53:
    await queue.SendMessageAsync(payload, cancellationToken);

    linie 54-58:
    zapis logu, ze wiadomosc zostala wyslana

Co robi ten kod?

Ten handler reaguje na zdarzenie utworzenia wizyty i wrzuca wiadomosc do Azure Queue Storage.

Nie wysyla maila sam. Tylko przygotowuje wiadomosc dla funkcji serverless.

Przyklad danych wrzucanych do kolejki:

    - appointmentId,
    - CustomerId,
    - HairdresserId,
    - SalonServiceId,
    - StartAt,
    - EndAt,
    - customerEmail,
    - customerName,
    - hairdresserName,
    - serviceName.

Po co uzywamy kolejki?

Kolejka oddziela proces tworzenia wizyty od procesu wysylania maila.

Bez kolejki:

    Klient tworzy wizyte -> API zapisuje wizyte -> API wysyla maila -> klient czeka

Z kolejka:

    Klient tworzy wizyte -> API zapisuje wizyte -> API wrzuca wiadomosc do kolejki -> klient szybko dostaje odpowiedz
    Azure Function pozniej odbiera wiadomosc i wysyla maila

To jest lepsze, bo wysylka maila moze byc wolna albo chwilowo niedostepna, a sama rezerwacja nadal moze zostac zapisana.

Dlaczego linia 31 jest wazna?

    MessageEncoding = QueueMessageEncoding.Base64

Azure Functions Queue Trigger w tej konfiguracji oczekuje Base64. Jawne ustawienie kodowania zmniejsza ryzyko problemow z odczytem wiadomosci.

Dlaczego linia 53 jest kluczowa?

    await queue.SendMessageAsync(payload, cancellationToken);

To jest faktyczne wyslanie wiadomosci do kolejki. Jesli ta linia sie wykona, w Azure Storage pojawia sie komunikat dla funkcji.

Co robi ten kod?

To jest Azure Function uruchamiana automatycznie, kiedy w kolejce booking-notifications pojawi sie nowa wiadomosc.

Nie trzeba wywolywac jej recznie przez HTTP. Mechanizm Azure Functions sam odpytuje kolejke i uruchamia metode Run.

Najwazniejsza linia:

    [QueueTrigger("booking-notifications", Connection = "AzureWebJobsStorage")]

Oznacza:

    - sluchaj kolejki booking-notifications,
    - polacz sie z Azure Storage przez zmienna AzureWebJobsStorage,
    - gdy pojawi sie wiadomosc, przekaz jej tresc do parametru message.

Po co uzywamy Azure Function?

Azure Function robi prace w tle. Nie obciaza requestu HTTP w API. Moze dzialac niezaleznie od App Service.

Co sie stanie, gdy funkcja ma blad?

Azure Functions sprobuje przetworzyc wiadomosc kilka razy. Jesli nadal sie nie uda, wiadomosc trafia do kolejki:

    booking-notifications-poison

To widzielismy podczas testow. Poison queue oznacza, ze funkcja odebrala wiadomosc, ale przetwarzanie zakonczylo sie bledem.

Dlaczego dodano try/catch?

Linie 37-46 pozwalaja zapisac dokladny blad do logow. Bez tego widzielibysmy tylko, ze wiadomosc trafila do poison queue, ale trudniej byloby znalezc przyczyne.

Dlaczego PropertyNameCaseInsensitive jest wazne?

API moglo wysylac JSON z polami typu:

    appointmentId
    customerEmail

a rekord w C# ma:

    AppointmentId
    CustomerEmail

Ustawienie case-insensitive pozwala poprawnie odczytac dane niezaleznie od wielkosci liter.

Co robi ten kod?

Ten kod wysyla maila z potwierdzeniem wizyty przez Azure Communication Services Email.

Najpierw sprawdza:

    - czy klient ma adres email,
    - czy konfiguracja email jest wpisana.

Jesli brakuje danych, funkcja nie wywala aplikacji, tylko loguje ostrzezenie i konczy prace.

Najwazniejsza linia:

    await client.SendAsync(WaitUntil.Started, emailMessage, cancellationToken);

Ta linia przekazuje maila do Azure Communication Services. WaitUntil.Started oznacza, ze kod czeka tylko do momentu rozpoczecia operacji wysylki po stronie Azure, a niekoniecznie do pelnego dostarczenia maila do skrzynki.

Dlaczego mail jest wysylany w Function, a nie w API?

Bo wysylka maila jest zadaniem pobocznym. Dla klienta najwazniejsze jest, aby wizyta zostala utworzona. Mail moze zostac obsluzony chwile pozniej w tle.

Co musi byc ustawione w Azure?

W booking-function musza istniec zmienne:

    Email__ConnectionString
    Email__SenderAddress
    AzureWebJobsStorage

Email__ConnectionString pochodzi z zasobu Azure Communication Services.

Email__SenderAddress to adres MailFrom z domeny email, np. DoNotReply@...azurecomm.net.

17. DLACZEGO TO JEST DOBRA ARCHITEKTURA?
----------------------------------------

1. API szybko odpowiada klientowi.

API nie musi czekac na pelna dostawe maila. Po zapisaniu wizyty wrzuca wiadomosc do kolejki.

2. Mail jest obslugiwany niezaleznie.

Jesli chwilowo wystapi problem z Azure Communication Services, wizyta nadal moze byc zapisana. Wiadomosc z kolejki moze byc ponowiona.

3. System jest latwiejszy do rozbudowy.

Mozna dodac kolejny handler, np. SMS, bez zmieniania kontrolera wizyt.

4. SignalR nie dubluje maili.

SignalR sluzy do powiadomien online, mail do potwierdzen offline.

5. Cosmos DB i Storage sa wywolywane asynchronicznie.

Serwer nie blokuje watkow podczas komunikacji z chmura.


18. CO POWIEDZIEC NA OBRONIE O WATKACH?
---------------------------------------

Mozesz powiedziec tak:

    "W aplikacji nie tworze recznie watkow przez Thread ani Task.Run. Zastosowalem model asynchroniczny ASP.NET Core oparty o async/await, Task i CancellationToken. Operacje sieciowe, takie jak Cosmos DB, Queue Storage, SignalR i Email, sa wykonywane asynchronicznie, dzieki czemu watki serwera nie sa blokowane."

Nastepnie:

    "Dodatkowo dluzsze zadania, takie jak wyslanie maila z potwierdzeniem wizyty, zostaly przeniesione do Azure Queue Storage i Azure Functions. API zapisuje wizyte i wrzuca komunikat do kolejki, a funkcja serverless odbiera go w tle i wysyla mail."

I jeszcze:

    "SignalR jest osobnym mechanizmem realtime. Wysyla natychmiastowe powiadomienie do podlaczonych klientow, ale nie zastepuje kolejki, bo SignalR nie jest mechanizmem trwalego przetwarzania."


19. NAJWAZNIEJSZE POJECIA
-------------------------

async:
Oznacza, ze metoda moze wykonywac operacje asynchroniczne i zwracac Task.

await:
Oznacza, ze kod czeka na zakonczenie operacji, ale nie blokuje watku.

Task:
Reprezentuje prace, ktora zakonczy sie w przyszlosci.

CancellationToken:
Pozwala przerwac operacje, np. gdy request HTTP zostanie anulowany.

Azure Queue Storage:
Kolejka komunikatow. Oddziela zapis wizyty od wysylki maila.

Azure Function:
Kod serverless uruchamiany automatycznie, gdy pojawi sie wiadomosc w kolejce.

Poison queue:
Kolejka bledow. Trafiaja tam wiadomosci, ktorych funkcja nie potrafila przetworzyc po kilku probach.

SignalR:
Technologia do komunikacji realtime z klientem.

Application Insights:
Monitoring i logi aplikacji.


20. JAKIE "WATKI" MOZNA WYROZNIC W APLIKACJI?
---------------------------------------------

1. Watek HTTP requestu
   Obsluguje wywolania Swagger/API.
   Przyklad: AppointmentsController.

2. Watek biznesowy rezerwacji
   Waliduje i zapisuje wizyte.
   Przyklad: AppointmentBookingFacade.

3. Watek zdarzeniowy
   Uruchamia reakcje po utworzeniu wizyty.
   Przyklad: BookingEventPublisher.

4. Watek kolejki
   Wrzuca komunikat do Azure Queue Storage.
   Przyklad: AzureQueueAppointmentBookedHandler.

5. Watek serverless
   Odbiera komunikat z kolejki i dziala w tle.
   Przyklad: AppointmentBookedQueueFunction.

6. Watek mailowy
   Wysyla potwierdzenie rezerwacji.
   Przyklad: AzureCommunicationEmailSender.

7. Watek realtime
   Wysyla powiadomienia przez SignalR.
   Przyklad: SignalRAppointmentBookedHandler i BookingNotificationsHub.

8. Watek dostepu do danych
   Obsluguje asynchroniczny CRUD w Cosmos DB.
   Przyklad: CosmosBookingRepository.


21. PODSUMOWANIE
----------------

W aplikacji zastosowano nowoczesny model asynchroniczny zamiast recznego zarzadzania watkami.

Najwazniejszy przeplyw:

    POST /api/Appointments
        -> AppointmentBookingFacade
        -> Cosmos DB
        -> BookingEventPublisher
        -> Azure Queue Storage
        -> Azure Function
        -> Azure Communication Services Email

Rownolegle:

    POST /api/Appointments
        -> SignalRAppointmentBookedHandler
        -> Azure SignalR Service
        -> powiadomienie realtime

Najwazniejsze korzysci:

    - aplikacja nie blokuje watkow serwera,
    - wysylka maila dziala w tle,
    - system jest odporniejszy na chwilowe bledy,
    - latwo dodac kolejne reakcje po utworzeniu wizyty,
    - SignalR daje powiadomienia natychmiastowe,
    - Azure Queue i Azure Function daja przetwarzanie niezawodne.
